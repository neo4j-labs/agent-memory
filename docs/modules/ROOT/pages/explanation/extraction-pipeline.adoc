= How Entity Extraction Works
:page-product: agent-memory
:page-pagination:
:toclevels: 2

Understanding the multi-stage extraction pipeline, trade-offs between speed and accuracy, and how extractors work together.

NOTE: This page describes the *client-side* extraction pipeline used by the *bolt* backend, which you configure (spaCy / GLiNER2.5 / LLM). On *NAMS*, extraction runs server-side and is not client-configurable — your extraction settings are ignored. See xref:explanation/backends.adoc#capability-matrix[Bolt vs NAMS].

== The Challenge

Entity extraction from natural language is hard. Consider this text:

> "Marc Andreessen and Ben Horowitz discussed their investment in OpenAI on the a]6z podcast. The San Francisco-based fund focuses on AI companies."

Humans easily identify: Marc Andreessen (person), Ben Horowitz (person), OpenAI (organization), a16z (organization), San Francisco (location), AI (technology/concept).

Machines need help.

== Three Extraction Approaches

neo4j-agent-memory supports three fundamentally different extraction approaches, each with trade-offs:

image::diagrams/extraction-pipeline.png[Multi-stage extraction pipeline: spaCy → GLiNER2.5 → LLM → relation validation → Knowledge Graph,width=540,align=left]

=== spaCy: Statistical NER

spaCy uses pre-trained statistical models to recognize entities.

[cols="1,1"]
|===
| Pros | Cons

| Very fast (native code)
| Fixed entity types (PERSON, ORG, GPE, etc.)

| No external API calls
| May miss domain-specific entities

| Free to run
| Lower accuracy on specialized text

| Runs offline
| No confidence scores
|===

*Best for*: Fast initial extraction, common entity types, offline use.

=== GLiNER2.5: Zero-Shot Joint Extraction

GLiNER2.5 (the `gliner2` package, `fastino/gliner2.5-++*++` checkpoints) extracts entities from type *descriptions* rather than training data, and decodes entities and relations together through its JointIE engine.

[cols="1,1"]
|===
| Pros | Cons

| Custom entity types via descriptions
| Slower than spaCy (neural network)

| Entities and typed relations in one pass
| Requires a model download (~407 MB for base-v1)

| Endpoint types enforced during decoding
| Relation recall collapses past ~400 words

| Confidence scores
| GPU recommended for speed

| Runs offline once the model is cached
| No coreference, so pronouns are never resolved
|===

*Best for*: Domain-specific extraction, custom types, typed relations without an LLM call.

[NOTE]
====
GLiNER v1 and the separate GLiREL relation model were removed in 0.7. "GLiNER" on its own now refers to that removed stack; the current extractor is `GLiNER2Extractor` on GLiNER2.5. See xref:how-to/migrate-to-gliner2.adoc[Migrate to GLiNER2.5].
====

=== LLM: Context-Aware Extraction

LLM extractors use large language models (GPT-4o, Claude, Llama, Gemini, …) with structured output.

[cols="1,1"]
|===
| Pros | Cons

| Best understanding of context
| Highest latency

| Can handle ambiguous text
| Most expensive (API costs)

| Explains reasoning
| Rate limits

| Most flexible
| May be inconsistent
|===

*Best for*: High-value extraction, complex text, when accuracy matters most.

[NOTE]
====
`LLMEntityExtractor` is provider-pluggable: pass any `LLMProvider` instance (Anthropic, Bedrock, Vertex AI, local Ollama, …) or rely on `MemorySettings.llm` to wire one for you. When the configured provider implements the Silver tier (`StructuredExtractor`), the extractor calls `complete_structured` with a Pydantic schema — OpenAI strict mode, Anthropic forced tool use, or schema-aligned retry, depending on the provider. See xref:explanation/structured-extraction.adoc[Structured Extraction] for the dispatch rules and xref:how-to/bring-your-own-model.adoc[Bring Your Own Model] for the wiring.
====

== Multi-Stage Pipelines

The real power comes from combining extractors in a pipeline:

[source,python]
----
from neo4j_agent_memory.extraction import ExtractionPipeline, MergeStrategy
from neo4j_agent_memory.ontology import POLEO_ONTOLOGY

pipeline = ExtractionPipeline(
    stages=[
        SpacyEntityExtractor(),                     # Fast first pass
        GLiNER2Extractor.for_schema("podcast"),     # Domain refinement + relations
    ],
    merge_strategy=MergeStrategy.CONFIDENCE,
    ontology=POLEO_ONTOLOGY,                        # Enables the validation stage
)
----

The default pipeline order is spaCy → GLiNER2.5 → LLM, followed by relation validation. Each stage is optional; a stage whose dependency is not installed logs a warning and is skipped.

=== Why Pipelines?

1. **Speed vs. Cost**: spaCy catches obvious entities instantly; GLiNER2.5 refines with domain knowledge and adds typed relations; the LLM handles the hard cases and preferences.

2. **Redundancy**: Multiple extractors provide confirmation. An entity found by both spaCy and GLiNER2.5 is more reliable.

3. **Coverage**: Different extractors have different strengths. spaCy finds common entities; domain schemas find specialized ones; only the LLM stage extracts preferences.

== Merge Strategies

When multiple extractors find entities, how do we combine results?

=== CONFIDENCE (Default)

Keep the entity with the highest confidence score:

[source,python]
----
# If spaCy finds "John" (0.85 default) and GLiNER2.5 finds "John Smith" (0.95)
# Result: "John Smith" with confidence 0.95
----

*Best for*: General use, when you trust confidence scores.

=== UNION

Keep all unique entities from all stages:

[source,python]
----
# spaCy:      ["John", "Acme"]
# GLiNER2.5:  ["John Smith", "Acme Corp", "NYC"]
# Result:     ["John", "John Smith", "Acme", "Acme Corp", "NYC"]
----

*Best for*: Maximum recall, when you'll filter/merge later.

=== INTERSECTION

Keep only entities found by more than one stage:

[source,python]
----
# spaCy:      ["John", "Acme"]
# GLiNER2.5:  ["John Smith", "Acme", "NYC"]
# Result:     ["Acme"]  # Only "Acme" found by both
----

*Best for*: High precision, when you only want confirmed entities.

=== CASCADE

Use the first stage's results and fill the gaps with later stages:

[source,python]
----
# spaCy's entities are kept as-is
# GLiNER2.5 and the LLM only add entities spaCy missed
----

*Best for*: Trusting a fast first stage while still improving coverage.

=== FIRST_SUCCESS

Stop at the first stage that returns entities:

[source,python]
----
# If spaCy finds entities, use them and skip the rest
# Otherwise try GLiNER2.5, then the LLM
----

*Best for*: Fast-first extraction with fallback, and for keeping LLM calls rare.

== Domain Schemas

GLiNER2.5's zero-shot capability becomes powerful with domain schemas - descriptions of entity types for your specific use case.

[source,python]
----
# The "podcast" schema (abridged)
{
    "person": "A person mentioned in the podcast, including hosts, guests, and people discussed",
    "company": "A company, startup, or business organization",
    "product": "A product, service, app, or software tool",
    "concept": "A business concept, methodology, framework, or strategy",
}

# The descriptions are read as annotation guidelines
extractor = GLiNER2Extractor.for_schema("podcast")
----

=== Why Descriptions Matter

GLiNER2.5 doesn't just match labels - it uses the semantic meaning of descriptions:

* `"person"` → Generic person detection
* `"A person mentioned in the podcast, including hosts, guests, and people discussed"` → Focuses on people in the interview context, not passing mentions

This is why domain schemas significantly improve extraction quality.

== Joint Entity and Relation Decoding

Beyond entities, GLiNER2.5 decodes typed relations in the *same* pass:

[source,python]
----
from neo4j_agent_memory.extraction import GLiNER2Extractor

extractor = GLiNER2Extractor.for_poleo()
result = await extractor.extract("Marc works at a16z in San Francisco")

# Entities:  [Marc, a16z, San Francisco]
# Relations: [Marc -[EMPLOYED_BY]-> a16z, a16z -[HEADQUARTERS_AT]-> San Francisco]
----

The ontology declares which endpoint types each relationship connects, and the JointIE decoder enforces that *during* beam search rather than filtering afterwards. An `EMPLOYED_BY` edge can only ever run from a person label to an organization label if that is what the ontology declared. Relations therefore come back carrying entity ids (`source_id`/`target_id`), and every endpoint is guaranteed to be one of the entities in the same result.

A consequence worth knowing: relations are only decoded when the ontology declares relationship types. The eight built-in domain catalogs are *label* catalogs; `poleo`, `podcast` and `news` carry relationships, the rest are entity-only until you attach some. See xref:reference/schemas.adoc[Domain Schemas Reference].

=== The Validation Stage

An ontology-aware pipeline runs one more step after merging: `ExtractionResult.validate_relations(ontology, mode="drop")`. Merging several stages can only ever *add* relations the ontology does not permit — the GLiNER2.5 stage constrains endpoints while decoding, the LLM and spaCy stages do not — so the last thing the pipeline does is throw those out and log how many.

=== Two Quiet Failure Modes

GLiNER2.5 has two ways of returning nothing that look like "there was nothing to find":

* **`feasible=False`** means the decoder could not satisfy the ontology's *hard* constraints (uniqueness, acyclicity) and fell back to an empty assignment. The extractor raises a `RuntimeWarning` saying so. The fix is to relax `unique_source`/`acyclic` or lower thresholds, not to conclude the text was empty.
* **Long input** silently loses relations. Recall degrades sharply past roughly 400 words and can reach zero while entity recall stays fine. The extractor windows anything longer than `max_words` (384) through `extract_long`, and relations whose endpoints land in different windows are dropped.

== Automatic Relationship Storage

When adding messages with entity extraction enabled, extracted relationships are automatically stored as `RELATED_TO` relationships in Neo4j:

[source,python]
----
# Relationships are stored automatically when adding messages
await memory.short_term.add_message(
    "session-1",
    "user",
    "Brian Chesky founded Airbnb in San Francisco.",
    extract_entities=True,
    extract_relations=True,  # Default: True
)

# This creates:
# - Entity nodes: Brian Chesky (PERSON), Airbnb (ORGANIZATION), San Francisco (LOCATION)
# - MENTIONS relationships: Message -> Entity
# - RELATED_TO relationships: (Brian Chesky)-[:RELATED_TO {type: "FOUNDED"}]->(Airbnb)
----

The relationship type name lives in `r.type`, and the merge key includes it — so one pair of entities can carry several differently-typed edges. `r.relation_type` is written as a mirror of `r.type` for one release; read `r.type`. Each edge also accumulates provenance: `support` (how many times it was observed), `derived`, `extractor`, `source_message_ids` (capped at 25) and `evidence` (capped at 3).

Edges written before 0.7 only carried `relation_type`. An idempotent backfill runs on connect and copies it into `r.type`; it matches nothing once every edge has been migrated.

The relationship storage works for:

* **`add_message()`** - Extract and store from individual messages (default: `extract_relations=True`)
* **`add_messages_batch()`** - Batch operations (default: `extract_relations=True`, only applies when `extract_entities=True`)
* **`extract_entities_from_session()`** - Post-hoc extraction from existing messages (default: `extract_relations=True`)

[source,python]
----
# Post-hoc extraction with relationship storage
result = await memory.short_term.extract_entities_from_session(
    "session-1",
    extract_relations=True,  # Default: True
)
print(f"Extracted {result['relations_extracted']} relationships")
----

=== Relationship Storage Strategies

Relationships can reference entities in two ways:

1. **Same-message entities**: When both the source and target entity are extracted from the same message, relationships are created using entity IDs (most efficient).

2. **Cross-message entities**: When a relationship references an entity from a previous message, the system looks up entities by name. This enables building a connected knowledge graph across a conversation.

== Performance Considerations

=== Latency

Typical extraction times for a 500-word document:

[cols="1,1,1"]
|===
| Extractor | CPU | GPU

| spaCy
| 10-50ms
| N/A

| GLiNER2.5 (base-v1)
| ~600ms
| 50-150ms

| LLM (GPT-4o-mini)
| 500-2000ms
| N/A
|===

The GLiNER2.5 CPU figure is measured: `benchmarks/compare_extractors.py` on the POLE+O gold set runs `fastino/gliner2.5-base-v1` at roughly 1.6 documents per second on CPU. `small-v1` is faster and `multi-v1` slower.

=== Batch Processing

For many documents, use batch extraction:

[source,python]
----
result = await pipeline.extract_batch(
    texts,
    batch_size=10,      # Texts per batch (memory management)
    max_concurrency=5,  # Parallel extractions
)
----

`GLiNER2Extractor.extract_batch()` decodes a slice of texts in one forward pass, which is where GPU batching pays off:

[source,python]
----
results = await extractor.extract_batch(texts, batch_size=32)
----

=== Streaming for Long Documents

For very long documents (>100K tokens), use streaming:

[source,python]
----
streamer = StreamingExtractor(
    extractor,
    chunk_size=4000,
    overlap=200,
)

async for chunk_result in streamer.extract_streaming(long_document):
    print(f"Chunk {chunk_result.chunk.index}: {chunk_result.entity_count} entities")
----

== Choosing the Right Approach

[cols="1,1,1,1"]
|===
| Scenario | Recommendation | Pipeline | Why

| Fast indexing, common entities
| spaCy only
| `[spaCy]`
| Speed, simplicity

| Domain-specific text
| GLiNER2.5 with a domain template
| `[GLiNER2.5]`
| Custom types, good accuracy

| High-value documents
| Full pipeline
| `[spaCy → GLiNER2.5 → LLM]`
| Maximum accuracy

| Mixed workload
| Tiered pipeline
| `[spaCy + GLiNER2.5]`
| Balance speed/accuracy

| Typed relations needed
| GLiNER2.5 on an ontology
| `[GLiNER2.5]`
| Entities and relations decode together, endpoints type-checked
|===

== Quality Expectations

Measured on the POLE+O gold set in `benchmarks/data/` with `benchmarks/compare_extractors.py` (CPU):

[cols="1,1,1,1", options="header"]
|===
| Checkpoint | Entity F1 | Relation F1 (lenient / strict) | Throughput

| `fastino/gliner2.5-base-v1`
| 0.80
| 0.37 / 0.27
| ~1.6 docs/s

| `fastino/gliner2.5-small-v1`
| 0.75
| _not measured_
| faster
|===

Both runs reported zero endpoint-type violations — the point of typed joint decoding. Entity F1 is roughly flat versus the GLiNER stack that came before; what 2.5 buys is typed joint decoding, long context and the boundary architecture, not a jump in entity accuracy. End-to-end zero-shot relation extraction is weak for every model in this class, so treat relation F1 as a floor to improve with per-relation thresholds rather than a finished number.
