= Apply a custom entity extraction schema
:page-product: agent-memory
:page-pagination:
:toclevels: 2
:sectanchors:

To identify customer and product mentions, provide domain descriptions and an explicit mapping from extraction labels to persisted entity types. Test the mapping against a representative sentence before writing graph data.

anchor:_prerequisites[]

== 1. Install the local extractor

Use Python 3.10 or newer and a POSIX shell. Prepare the example files and install the required extra:

include::partial$python-tutorial-setup.adoc[]

[source,bash]
----
python -m pip install 'neo4j-agent-memory[gliner]==0.6.0'
----

The maintained program `extraction_recipes.py` supplies its own imports, source texts, and event-loop entry point. It downloads the GLiNER model on first inference; allow disk space and network access for the download. These commands do not connect to a database or require an LLM API key.

include::partial$python-extraction-recipe-file.adoc[]

== 2. Configure and run the extraction

The custom schema names `customer` and `product`. Its mapping uses `(TYPE, SUBTYPE)` tuples: a customer maps to PERSON and a product to OBJECT/PRODUCT. `for_schema` is reserved for registry names; a custom `DomainSchema` is passed to the constructor.

The following function is included from the complete program. Run the maintained file with the command below it.

[source,python]
----
include::example$extraction_recipes.py[tags=schema;extract]
----

[source,bash]
----
python extraction_recipes.py schema
----

== 3. Verify the result

Expected: candidates from “Maya Chen bought a Trail Starter shoe,” with PERSON and/or OBJECT/PRODUCT types, then the verified candidate count. Model output can omit or misidentify a mention; inspect it before using the schema on a corpus.

The command raises on the documented failure conditions. Inspect candidate names, types, and confidence against source text before storing them. Counts alone do not measure extraction accuracy.

anchor:_available_built_in_schemas[]

== Select a registered schema when it fits

Registered names are `poleo`, `podcast`, `news`, `scientific`, `business`, `entertainment`, `medical`, and `legal`. The exact label inventories and descriptions are in xref:reference/schemas.adoc[built-in schemas]. There are no registered `financial` or `ecommerce` names. Use a custom schema for those domains.

`DomainSchema` configures GLiNER label descriptions and optional relation descriptions. `EntitySchemaConfig` is the separate SDK schema configuration model; do not interchange the two or pass unsupported `examples` fields. `ExtractorBuilder.with_schema` forwards type names, not every constraint and relation in a schema configuration. See xref:reference/schemas.adoc[schema models and persistence] before relying on validation.

anchor:_relationship_extraction[]

== Extract relationships and persist schema configuration

For GLiREL, install `glirel`, spaCy, and the `en_core_web_sm` tokenizer model, construct `GLiRELExtractor(relation_types=...)`, and compose it with the entity extractor. A custom domain object's existence does not automatically wire a relation extractor. The xref:tutorials/knowledge-graph.adoc[knowledge-graph tutorial] includes every dependency and the complete constructor/storage path.

Persisting an `EntitySchemaConfig` through the Bolt schema manager stores configuration; it does not automatically validate every existing graph node or deploy a hosted ontology. Select/load the intended configuration explicitly when constructing extraction. See xref:reference/schemas.adoc[the persistence API] and xref:how-to/use-ontologies.adoc[hosted ontology tasks] for the separate contracts.
