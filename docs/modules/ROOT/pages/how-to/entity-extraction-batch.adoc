= Account for batch and chunk extraction results
:page-product: agent-memory
:page-pagination:
:toclevels: 2
:sectanchors:

include::partial$backend-bolt-only.adoc[]

To process multiple source texts without losing failed inputs, use the pipeline's batch result wrappers and retain the input index for every result. For longer individual texts, select explicit chunk units and inspect per-chunk errors.

For the rationale, see xref:explanation/extraction-pipeline.adoc[Understanding the extraction pipeline].

anchor:_prerequisites[]

== 1. Install the local extractor

Use Python 3.10 or newer and a POSIX shell. Prepare the example files and install the required extra:

include::partial$python-tutorial-setup.adoc[]

[source,bash]
----
python -m pip install 'neo4j-agent-memory[gliner]==0.6.0'
----

The maintained program `extraction_recipes.py` supplies its own imports, source texts, and event-loop entry point. It downloads the GLiNER model on first inference; allow disk space and network access for the download. These commands do not connect to a database or require an LLM API key.

include::partial$python-extraction-recipe-file.adoc[]

== 2. Configure and run the extraction

The runner selects the `business` GLiNER schema. `ExtractionPipeline(..., fallback_on_error=False)` propagates an extractor error to the batch wrapper; `fail_fast=False` then collects the item error instead of abandoning the remaining inputs. The example starts with one worker and a batch size of two; tune after measuring your workload.

The following function is included from the complete program. Run the maintained file with the command below it.

[source,python]
----
include::example$extraction_recipes.py[tags=batch]
----

[source,bash]
----
python extraction_recipes.py batch
----

== 3. Verify the result

Expected: progress for both inputs, an `Input ...` line for each result, and `Verified: all 2 inputs accounted for`. Failed items are printed with their source indexes and cause a nonzero exit so they can be retried after correcting the cause. An empty but successful extraction is still an accounted-for item; inspect it for quality.

The command raises on the documented failure conditions. Inspect candidate names, types, and confidence against source text before storing them. Counts alone do not measure extraction accuracy.

anchor:_streaming_extraction[]

== Process a long text in chunks

. Read the maintained streaming function:
+
[source,python]
----
include::example$extraction_recipes.py[tag=streaming]
----
. Run it against the program's repeated fictional sample text:
+
[source,bash]
----
python extraction_recipes.py streaming
----
. Verify `Verified: ... chunks completed; ... merged entities`. Any chunk error raises with its chunk index; inspect candidate quality separately.

`chunk_size=400` and `overlap=40` in this example are *characters*. The default is 4,000 characters with 200 overlap. With `chunk_by_tokens=True`, this implementation uses approximate whitespace token counts, not the exact tokenizer of every model. Choose a size based on the selected model's accepted input, boundary behavior, memory use, latency, and a representative corpus; there is no universal 2,000/10,000/100,000-token cutoff.

The API accepts the complete input string and computes its chunks. It is not a file-streaming reader that avoids loading the document text into memory. `extract_streaming` yields `StreamingChunkResult` objects with `.result.entities`; `extract` returns `StreamingExtractionResult`, and `to_extraction_result` converts it to the common result model. Calling extraction twice repeats model work.

anchor:_track_extraction_quality[]

== Preserve source indexes and measure quality

The batch API shown here belongs to `ExtractionPipeline`. `GLiNEREntityExtractor.extract_batch` has a different signature and returns a list of `ExtractionResult`, not the aggregate wrapper. Keep the two APIs distinct.

Before persistence, associate each successful `BatchItemResult.index` with its source document; log errors against that same input identifier. The xref:tutorials/knowledge-graph.adoc[document program] demonstrates message provenance and safe relationship endpoint matching. Measure precision/recall on reviewed samples and inspect chunk boundaries; a 100% completed-item rate is not a claim of extraction accuracy.

See xref:reference/extractors.adoc[batch, stage, and streaming result models] and xref:how-to/batch-processing.adoc[document-processing tasks].
