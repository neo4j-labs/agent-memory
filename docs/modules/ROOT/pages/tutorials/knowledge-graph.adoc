= Build a knowledge graph from documents
:page-product: agent-memory
:page-role: code-nocollapse
:page-pagination:
:toclevels: 2
:sectanchors:

We will extract candidate entities and relationships from two fictional business documents, store their message provenance, inspect the graph after restarting Python, and pass that evidence to a chat model. We will inspect model output rather than assume every extraction is correct.

This lesson uses `neo4j-agent-memory` 0.6.0 from PyPI, the complete programs on this page, and a dedicated Neo4j AuraDB instance over Bolt. Offline contract tests exercise their assembly and control flow; provider and database success still need to be observed in your environment.

anchor:_prerequisites[]

== Before you begin

* Python 3.10 or newer and a POSIX shell such as Bash or Zsh.
* An OpenAI API key with access to `text-embedding-3-small`.
* A Neo4j Aura account with capacity for a dedicated AuraDB Free instance.

The embedding calls send the supplied text to OpenAI. This exercise uses fictional data. Neo4j Agent Memory is an experimental Neo4j Labs project; see xref:reference/backend-capabilities.adoc[backend capabilities] before adapting the example to NAMS.

You also need an OpenAI chat-model ID and disk space/network access for the GLiNER, GLiREL, and spaCy model downloads. CPU inference and the first download can take several minutes. The install command below adds `glirel` and `loguru` alongside the SDK extras; see xref:reference/extractors.adoc#_glirelextractor[the GLiRELExtractor reference] for why those two packages are named explicitly.

== 4. Inspect the documents and custom extractor

Read `knowledge_graph.py` from step 1. `ingest()` runs the extractor; `store_document()` uses public `short_term.add_message()`, `long_term.add_entity()`, `add_relationship()`, and `link_entity_to_message()` calls. `inspect_graph()` verifies source messages and triples through `get_conversation()` and `query.cypher()`. The filename/name maps and assertions are tutorial verification scaffolding.

We construct `GLiNEREntityExtractor(schema=SCHEMA)` and `GLiRELExtractor(relation_types=SCHEMA.relation_types)` explicitly, then compose them. `for_schema()` accepts a registered schema name, not an arbitrary schema object. The label mapping maps custom labels to `(TYPE, SUBTYPE)` tuples.

The command help from the assembly checkpoint lists `ingest`, `inspect`, and `answer`. The source documents are constants in the file; there is no missing input directory to create.

== 5. Extract and store the documents

[source,bash]
----
python knowledge_graph.py ingest
----

Expected: candidate names and stored/skipped counts for each document, followed by `Verified: extraction produced storable relationships`. Entity names and relationship counts can vary. If no entities or resolved relationships are produced, the program stops with a diagnostic; inspect the text and extraction settings before starting again with a fresh database.

Every extracted mention receives an `EXTRACTED_FROM` link to its source message. Relationship endpoints must match unambiguous names in the same extraction result. Unresolved or ambiguous endpoints are reported and skipped. Bolt merges exact name/type matches across documents even when semantic deduplication is disabled. In SDK 0.6.0, `add_entity()` returns the canonical stored ID. The program additionally reads the exact name/type match to verify its identity and reject ambiguity before attaching links. Variants and aliases remain a separate xref:how-to/deduplication.adoc[deduplication] task.

== 7. Inspect the physical graph

In the Aura console, open *Query*, select the lesson instance and database, and connect with the credentials exported in step 2. Run:

[source,cypher]
----
MATCH (c:Conversation {session_id: 'docs-knowledge-sources'})-[:HAS_MESSAGE]->(m:Message)<-[:EXTRACTED_FROM]-(e:Entity)
RETURN c, m, e
----

Expected: both source messages linked to extracted entities. Then inspect relationship properties:

[source,cypher]
----
MATCH (a:Entity)-[r:RELATED_TO]->(b:Entity)
RETURN a.name, r.type, b.name, r.confidence
----

Expected: the same stored triples printed by `inspect`, each with a nonempty logical relationship name. This lesson saves extracted candidates through explicit `add_relationship` calls, which store that name in `RELATED_TO.type`; they do not create a physical `works_at` relationship type. Automatic message extraction uses the separate `RELATED_TO.relation_type` property. `attributes` passed to `add_relationship` are currently not persisted by this write path, so provenance is stored through the dedicated message link instead. `add_relationship` raises `NotFoundError` when either endpoint id matches no `:Entity` node, rather than silently creating an edge the graph does not contain — one reason `store_document` verifies each candidate's stored id before attaching a link.

== 8. Answer from retrieved evidence

[source,bash]
----
python knowledge_graph.py answer
----

Expected: readback milestones followed by `Answer using retrieved evidence (inspect its factual accuracy):` and the model response. Compare the answer to the two fictional source texts, including Maya Chen's role and Denver. == What we built

We constructed a custom extraction pipeline, preserved document provenance, verified the persisted graph in a separate process, and used retrieved evidence in a model request. See xref:how-to/entity-extraction-schemas.adoc[custom extraction schemas], xref:how-to/entity-extraction-batch.adoc[batch extraction], and xref:reference/extractors.adoc[extractor contracts] for task-specific extensions.
